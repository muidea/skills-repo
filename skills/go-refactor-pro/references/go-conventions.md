# Go 重构约定

## 先服从目标仓库

- 以目标仓库的 `go.mod`、格式化、lint、错误、日志、目录和测试约定为准。
- 不因为 Go 新版本提供了新特性就主动迁移既有实现。
- 不在纯重构中扩大 exported API、配置面或序列化格式。
- 标准库和简单具体实现通常优先于新依赖和新抽象。

## 模式选择

### 泛型

适用于多个已存在实现共享同一算法、类型集合稳定、调用方更清晰的情况。不适用于仅有一个调用点、业务语义不同或需要复杂约束才能复用的逻辑。

### Functional Options

适用于可选配置较多、组合持续扩展、需要保留构造兼容性的对象。固定且必需的少量依赖继续使用显式参数或配置结构体；参数数量本身不决定模式。

### 接口

接口通常由消费者定义，并保持最小。只有存在真实替换点、外部系统边界或测试需要隔离副作用时才引入；不要为单一实现提前设计 provider 层级。

### 日志与错误

- 保持仓库既有日志合同；只有明确迁移任务才统一到 `log/slog`。
- 使用 `%w` 保留单一错误链。
- 只有多个独立操作都必须执行且错误都需要保留时才使用 `errors.Join`。
- 不在纯重构中改变错误类型、错误码或调用方可观察的匹配行为。

## 可读性与所有权

- 优先让数据和状态由单一组件拥有，避免共享可变状态。
- 提取 helper 前确认它表达稳定概念，而不是偶然相似的几行代码。
- 抽象导致调用路径更长、命名更泛或业务约束更隐蔽时，保留具体实现。
- 删除死代码、无效层和透传包装通常比新增设计模式更有价值。
